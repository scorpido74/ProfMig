# Error Handling and Recovery

## Overview

ProfMig uses a centralized error handling and recovery framework to provide
consistent error classification, recovery behavior, logging, reporting and
process exit codes.

The framework is designed to prevent individual file or application failures
from unnecessarily terminating an entire profile migration, while ensuring
that critical failures stop the migration safely.

This functionality was introduced as part of Sprint 3.6.

---

## Design principles

The ProfMig error handling framework follows these principles:

- Critical failures must stop the migration safely.
- Individual file failures should not terminate the complete migration when
  they can safely be isolated.
- Retryable operations use bounded retries.
- Existing destination files must not be overwritten unexpectedly.
- Failed copies must not leave incomplete files under their final filename.
- Structured error information must be preserved through copy operations,
  application migration, logging and reporting.
- Logging failures must never replace or hide the original application error.
- Operational logs should avoid unnecessary exposure of source and destination
  profile paths.
- Process exit codes must remain predictable for scripts and automation.

---

## Error model

ProfMig represents errors using a structured error object.

The standard error object can contain:

- Timestamp
- Category
- Severity
- Component
- Operation
- Message
- Reason
- SourcePath
- DestinationPath
- ExceptionType
- HResult
- Retryable
- RetryCount
- RecoveryAction
- Critical

This allows errors generated by different ProfMig components to be handled
consistently.

---

## Error categories

ProfMig defines the following error categories:

| Category | Description |
| --- | --- |
| ConfigurationError | Missing, invalid or unreadable ProfMig configuration |
| ValidationError | Pre-migration or environment validation failure |
| PermissionError | File system or profile permission failure |
| SourceReadError | Failure while reading source data |
| DestinationWriteError | Failure while writing destination data |
| FileLocked | Source file is locked or in use |
| InsufficientStorage | Insufficient destination storage |
| ApplicationMigrationError | Application-specific migration failure |
| VerificationError | Migration or copy verification failure |
| UnexpectedError | Unexpected or unclassified failure |

Known and predictable failures should use one of the defined categories rather
than being reported as `UnexpectedError`.

## Severity levels

ProfMig uses four severity levels:

| Severity | Meaning |
| --- | --- |
| Information | Informational condition; no failure |
| Warning | Recoverable condition or isolated migration issue |
| Error | An item or migration component failed |
| Critical | Migration cannot safely continue |

Critical errors normally use:

```text
Severity       : Critical
RecoveryAction : Stop

Recovery actions

The centralized recovery model supports the following recovery actions:

Recovery action	Meaning
None	No recovery action required
Retry	Retry the failed operation
Skip	Skip the failed item and continue
Stop	Stop the migration
ReRun	The operation or migration must be run again

The recovery action describes what ProfMig should do after handling the error.

Retry behavior is additionally represented using:

Retryable
RetryCount

For example, when a locked file remains unavailable after three retries:

Category       : FileLocked
Severity       : Warning
Retryable      : True
RetryCount     : 3
RecoveryAction : Skip

This indicates that the condition was retryable, three retries were performed
and the file was ultimately skipped.

File copy recovery

File copy operations use bounded retry behavior for retryable failures.

The current default behavior is:

Perform the initial copy attempt.
Retry a retryable failure up to three times.
Wait two seconds between retries.
Skip the file when all retries are exhausted.
Continue the migration when the failure is not critical.

The retry limit prevents ProfMig from becoming stuck indefinitely on an
unavailable or locked file.

A single locked file must therefore not terminate the complete profile
migration.

Locked files

Locked files are classified as:

Category  : FileLocked
Severity  : Warning
Retryable : True

ProfMig retries the operation according to the configured retry policy.

When the file remains locked after all retries, the failed item is recorded and
the migration can continue.

When the file becomes available during the retry window, the copy operation can
complete normally.

Safe staged file copy

ProfMig uses a staged copy mechanism to prevent incomplete destination files.

Instead of copying directly to the final destination filename, data is first
written using a temporary filename with the suffix:

.profmig-partial

For example:

Document.docx.profmig-partial

After the copy succeeds, the temporary file is promoted to the final
destination filename.

This prevents an interrupted or failed copy operation from leaving a partially
copied file that appears to be valid.

Partial-file recovery

A stale .profmig-partial file from an earlier interrupted operation can be
recovered safely.

ProfMig can remove or replace the stale partial file before retrying the copy.

The source file is not modified as part of this recovery process.

After a successful copy:

The final destination file exists.
The .profmig-partial file no longer exists.
Existing destination files

ProfMig does not automatically overwrite an existing destination file.

When the final destination file already exists:

The source file is not copied over it.
The existing destination data is preserved.
The item is recorded as skipped.
No .profmig-partial file remains.

This prevents ProfMig from unexpectedly destroying existing destination data.

Permission errors

File system access failures can be classified as:

Category       : PermissionError
Severity       : Error
Retryable      : False
RecoveryAction : Skip

ProfMig is intended to be executed with sufficient administrative privileges.

However, administrative privileges do not guarantee that every source or
destination object is immediately accessible. File system ACLs, ownership,
locked files and profile permissions may still affect migration operations.

Permission handling and ACL repair functionality introduced in Sprint 3.5 is
used alongside the Sprint 3.6 error handling framework.

Configuration errors

Configuration problems are classified as ConfigurationError.

Examples include:

Missing Config.psd1
Invalid or unreadable configuration
Missing application definition folder
Invalid application definitions

These errors are critical because ProfMig cannot reliably determine the
migration configuration.

Typical handling is:

Category       : ConfigurationError
Severity       : Critical
RecoveryAction : Stop
Exit code      : 3
Validation errors

Blocking pre-migration validation failures use ValidationError.

For example:

Category       : ValidationError
Severity       : Critical
RecoveryAction : Stop

ProfMig must not start a migration when the validation result indicates that
the migration cannot safely proceed.

A validation warning does not automatically block migration.

Insufficient storage

Insufficient destination storage is treated separately from a generic
validation failure.

Example:

Category       : InsufficientStorage
Severity       : Critical
RecoveryAction : Stop
Exit code      : 6

This allows automation and reporting to distinguish insufficient storage from
other validation failures.

Application migration errors

Application migration results are normalized to the same structured error
model used by the core migration framework.

When a CopyEngine error already contains structured Sprint 3.6 error
information, that classification is preserved.

For example, a locked file encountered during Chrome migration remains:

Category : FileLocked

rather than being converted into a generic application error.

Application-specific failures without an existing structured classification
are represented as:

Category       : ApplicationMigrationError
Severity       : Error
RecoveryAction : Skip

This provides consistent reporting across profile and application migration.

Logging

Structured ProfMig errors are integrated with the normal ProfMig logging
framework.

A structured log entry can contain:

Category
Severity
Component
Reason
Recovery action
Error message

Example:

[ERROR] [Category=ValidationError | Severity=Critical | Component=ProfMig | Reason=PreMigrationValidationFailed | Recovery=Stop] Pre-migration validation failed.

Source and destination profile paths are not included in the normal structured
log message.

This reduces unnecessary exposure of usernames and profile locations in
operational logs.

Logging failure handling

Top-level error logging is best-effort.

Startup may fail before the logging subsystem has been fully initialized.

A logging failure must therefore never replace or hide the original ProfMig
error.

When structured logging is unavailable, ProfMig still provides console output
for the original failure.

Reporting

Structured error information is preserved in migration reporting.

Failed items can include:

Component
Source
Destination
Category
Severity
Reason
Recovery action
Critical state
Retryable state
Retry count
Exception type
Error message

The report also provides a human-readable error summary.

Example:

Sprint36ReportingTest [FileLocked] : The source file is locked by another process.

This makes the report useful both for troubleshooting and for automated result
processing.

Process exit codes

ProfMig provides stable process exit codes for scripts, deployment tools and
automation.

Exit code	Result
0	Success
1	SuccessWithWarnings
2	MigrationFailed
3	ConfigurationError
4	ValidationError
5	PermissionError
6	InsufficientStorage
7	VerificationError
8	ApplicationMigrationError
99	UnexpectedError
Migration result codes

Exit codes 0 through 2 describe the overall migration result:

0 = Success
1 = SuccessWithWarnings
2 = MigrationFailed
Known failure codes

Exit codes 3 through 8 identify known failure categories.

These allow deployment or automation systems to distinguish, for example, a
configuration problem from insufficient storage.

Unexpected failures

Exit code 99 is reserved for unexpected or unclassified failures.

Known and predictable conditions should not use exit code 99.

Startup error handling

Known startup failures are converted to structured ProfMig exceptions.

Examples include:

ConfigurationFileNotFound
ApplicationDefinitionFolderNotFound
InvalidApplicationDefinitions
NoUserProfilesFound

These failures retain their category, severity, recovery action and reason when
they reach the top-level application error handler.

The top-level handler then:

Reads the ProfMig exception metadata.
Creates a standardized error object.
Determines the process exit code.
Attempts to write the structured error to the session log.
Displays a concise console error.
Terminates ProfMig using the appropriate exit code.
Privacy considerations

Operational logging intentionally avoids including source and destination paths
in the standard structured error message.

Detailed migration reports can contain source and destination information where
this is required for troubleshooting.

This separation provides useful diagnostic information while reducing
unnecessary exposure of profile names and paths in routine log files.

Result

Sprint 3.6 provides ProfMig with a consistent error handling and recovery
foundation.

Known failures are classified instead of being treated as generic exceptions,
recoverable file failures can be isolated without terminating the complete
migration, critical failures stop processing safely, and structured error
information is preserved through logging and reporting.

The framework also provides stable exit codes that can be used by future
automation and deployment workflows.
